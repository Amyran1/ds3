The Perf Bounty Agent

A sidecar agent that fires after every harness run, treats the deterministic output of run X as a frozen oracle, and tries to win the biggest speedup it can without changing the answer. Same idea, narrower gate, for feature builds.

2 The loop — perf agent is a sidecar fork, not a blocker

Autoloopmain thread
iter N: plan → build feature → run_NN.py → harness_response.json frozen → iter N+1: plan
Perf Bountyfork, async
↳ spawn read timing ledger → pick bottleneck → propose patch → replay run X → equivalence check → ✓ merge + log win
If failon the same lane
↳ log attempt to perf_attempts.jsonl → no merge, no churn → technique marked tried for (file, bottleneck)
Key property: the bounty agent never blocks the main autoloop. iter N+1 starts whether the patch lands or not. Wins accrue in the background.

3 When to fire — harness always, features gated

Harness — fire on every run

Harness shape is uniform across runs. Same stages, same response contract. Pattern reuse is high. Always cheap to try; wins compound across the whole project.

Feature builds — fire when worth it

Feature code is heterogeneous. Some families finish in 8s. Some take 40 min. Spending agent budget on the fast ones is waste.

on every harness run: fire bounty agent # uniform, deterministic, always pays back on every feature build (after cache.put): if total_seconds > 60 OR rows_per_second < 100 OR cache_size_mb > 500 OR matches_pattern(prior_win): fire bounty agent else: skip — record "fast enough" in feature_perf.jsonl after 3 failed attempts on same (file, bottleneck_stage): cool down: do not retry for 5 iterations

4 The equivalence contract — what "same answer, faster" means

Frozen inputs (run X oracle)

  • Same input dataframe (parquet hash pinned)
  • Same model config, same seed
  • Same outcome version, same feature dictionary
  • Same git_sha for non-perf code
≡

Required equalities (modified code)

  • predictions.parquet hash equal — OR row-wise corr > 0.99999
  • Headline metric within 1e-6 absolute
  • All HarnessResponse fields equal modulo performance.* and timestamps
  • For features: cache parquet hash equal, column-by-column
Win condition: equivalence passes and wall time drops by ≥ 10% on the same sample tier. Below 10% is "noise win", logged but not merged. ≥ 25% is a celebrated win.

6 The pretend incentive — make the agent want the biggest win

Score function

score = log2(speedup) · seconds_saved · equivalence_strict — rewards big multipliers on slow targets, zero for drift.

Per-technique leaderboard

Group wins by technique tag (parallelize / vectorize / batch / prune / cache). The agent reads its own history and prefers proven moves over novel ones for the same bottleneck shape.

Cumulative dashboard

"Hours of compute saved since autoloop started." Single number, surfaced in the daily slack ping. This is the visible win the user cares about.

7 Knowledge library — one-off features, shared patterns

The asymmetry

Feature code is one-off. Feature bottlenecks fall into ~12 recurring shapes (row-wise apply with API, sync IO loop, np↔pd roundtrip, missing batch, unindexed merge). The library lives at the shape layer.

A. Recipe catalog — start here

Markdown files under libs/autoloop/perf_recipes/. One per technique: name, fingerprint, before/after, libs, expected speedup, drift pitfalls. Curated; auto-promotion rule suggests new recipes after 3 wins of the same technique.

B. Champion diff bank — start here

Every merged win auto-saved as a unified diff plus metadata (fingerprint, speedup, equivalence proof). Retrieved at fire-time by fingerprint match, injected as few-shot examples in the agent prompt.

C. AST / regex fingerprints — start here

Small Python rules file. Deterministic: has_iterrows_with_api_call(node) → tag row_wise_sync_io. Cheap, fast, routes bottlenecks to relevant recipes and diffs.

D. Tried-and-failed ledger — the moat

Extends perf_attempts.jsonl with failure_reason, drift_pct, fingerprint. Cross-project visible. Saves more budget over a year than any positive recipe does — winning techniques are obvious, knowing what's broken isn't.

E. Repo antipattern doc — defer

Human prose at knowledge/perf-antipatterns.md. The "why" stories that don't fit a diff. Integrates with existing retro flow. Compounds slowly.

F. Vector search (Pinecone) — defer until ~20 wins

Embed (before_code, technique). Earns its keep when code shapes blur and fingerprints stop discriminating cleanly. Pinecone already in Container.

Lookup flow: fingerprint slow code (C) → pull top-3 champion diffs same tag (B) → drop already-tried failures for this (fingerprint, project) (D) → read recipe if one exists (A) → propose patch → equivalence check → write back to all four. Every win + every failure makes the next call cheaper.

All four primary stores live at repo root (not per-project), so a win in civic_shout teaches the next project automatically.

8 Risks and how the design absorbs them

False-positive equivalence

Float-order drift on parallel reductions can pass corr>0.99999 but break downstream gap-finder slicing. Mitigation: equivalence check runs gap-finder on both outputs; any slice population shift > 0.1% rejects.

Code churn / merge conflicts

Frequent harness edits collide with feature-engineering commits. Mitigation: perf commits land on perf/auto-N branches, are merged only between autoloop iterations, and a single "active perf branch" rule prevents pile-up.

Agent over-optimizes the smoke run

10% wins on a 1% sample may not generalize. Mitigation: equivalence + speedup must hold at the next-tier-up sample before merge. Smoke alone is "candidate", not "win."

Bounty agent re-derives the wheel

Same parallelization tried 5 runs in a row. Mitigation: perf_attempts.jsonl records every tried (file, bottleneck, technique) tuple including failures, fed back into the agent prompt as "already tried."
